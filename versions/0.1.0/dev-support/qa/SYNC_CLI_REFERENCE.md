# Справочник репозиторного скрипта (полная версия)

Читать для Git-задачи, продолжения операции, реестра задач или разбора конкретного исключения. Обычная игровая задача ограничивается корневым [SYNC_TOOL.md](../../../../SYNC_TOOL.md).

Владельцы: CLI — [sync.mjs](../../../../tools/sync.mjs); операции/продолжение/журнал — [sync-engine.mjs](../../../../tools/sync-engine.mjs); Git/файлы/lock/проверки/среда — [sync-support.mjs](../../../../tools/sync-support.mjs); реестр задач и планы — [sync-tasks.mjs](../../../../tools/sync-tasks.mjs); замеры — [sync-bench.mjs](../../../../tools/sync-bench.mjs); регрессии — [sync.test.mjs](../../../../tools/sync.test.mjs).

## Обычная цепочка

```text
sync task register --task TASK --file PATH      # заявить владение точными файлами
sync task ready --task TASK                     # явно подтвердить готовность порции
sync plan --task TASK                           # заморозить план: SHA, fingerprints, файлы, свои commits
sync publish --plan PLAN_ID                     # сохранить, объединить, проверить, отправить
```

`task register` и `task ready` пишут только локальный реестр, не обращаются к сети и не создают commits. `plan` не обращается к сети: он использует уже наблюдённый `origin/main`. `publish --plan` — единственный шаг, который может отправить изменения, и только по прямому поручению пользователя.

## Продолжение после конфликта

```text
sync publish --continue OPERATION_ID
```

Одно продолжение оформляет разобранное разрешение, проверяет итог и отправляет его. Отдельный `resolve` остаётся локальным действием и никогда не начинает push:

```text
sync resolve --operation OPERATION_ID   # оформить и проверить разрешение локально
sync publish --continue OPERATION_ID    # отправить уже проверенный итог
```

`--continue` принимает исходную операцию в состоянии `conflict` (разрешение ещё не оформлено) или `updated` (разрешение уже оформлено локально). Порядок действий участника:

1. Открыть `report.json` и указанный `workspace`.
2. Отредактировать **только** перечисленные конфликтные файлы; посторонние правки и новые файлы запрещены.
3. Запустить `publish --continue OPERATION_ID`.

Отказы продолжения: `foreign-operation` (ID другой копии или другого автора), `changed` (история источника сдвинулась), `conflict` (остались маркеры), `not-resumable` (операция не была конфликтом), `verification-failed` (этот же результат уже не прошёл проверку), `paused`, `current` (уже опубликовано).

## Подтверждение проверки

Каждый прогон проверок записывается в `verifications` отчёта операции: точный `commit` и `tree`, профиль (`check` или `check:game`), состав профиля, версия инструмента и его fingerprint, Node/Git/ОС, хеши `ENGINE_LOCK.json` и `package-lock.json`, `installId` установленных зависимостей, путь к логу и время.

Правила переиспользования:

- только в пределах одной цепочки операций (конфликт → продолжение), никогда между машинами и разными задачами;
- только при совпадении дерева, профиля и всех полей среды;
- неуспешное подтверждение не переиспользуется: тот же результат повторно не проверяется, пока причина не изменится;
- если remote продвинулся, новые изменения объединяются; изменившееся дерево проверяется заново, неизменное — нет;
- внутри одной операции одинаковое дерево проверяется один раз.

## Реестр задач

`<общий Git-каталог>/gamejam-sync/tasks/<taskId>.json`: `taskId`, автор, исходный commit, точные файлы, состояние `open`/`ready`/`published`, свои checkpoints и планы.

- Файл принадлежит одной незавершённой задаче. Совпадение возвращает `ownership-conflict`; смешанные фрагменты внутри файла скрипт не распределяет.
- `taskId` — 1–64 символа `A-Za-z0-9._-`; выход за каталог реестра невозможен.
- Готовность отмечается явно; дата и наличие изменений её не заменяют.

## Планы

`<общий Git-каталог>/gamejam-sync/plans/<planId>.json` неизменяем: `planId`, `taskId`, автор, `baseHead`, наблюдённый remote, точные файлы, `fileSnapshot`, свои checkpoints, чужие неопубликованные commits, профиль проверки и сообщение.

- `plan-stale` — изменились выбранные файлы или `HEAD`; молча расширять план нельзя, нужен новый `plan`.
- `approval-required` — в истории есть commits без метки `Task: TASK`; их нужно просмотреть и перечислить явно через `--commit`.
- Повторный `publish --plan` для уже опубликованного плана возвращает `current` и ничего не отправляет.
- Удаления и переименования входят в план как точные пути обеих сторон.

## Совместимый request JSON

```json
{
  "taskId": "npc-visuals",
  "actor": "ereti",
  "message": "Обновил согласованные визуалы NPC",
  "files": ["src/example.ts", "assets/example.png"],
  "commits": [],
  "expectedHead": "полный локальный SHA",
  "expectedRemote": "полный удалённый SHA",
  "expectedFiles": "fileSnapshot"
}
```

`--request FILE` принимает те же поля плюс `operationId`, `continueOperation`, `planId`, `maxAttempts`, `limit`. Смешивать request-файл и отдельные флаги нельзя. Пути — только точные относительные; каталоги, glob, `.git`, ignored-файлы и обходы путей отклоняются.

## Состояния

| Состояние | Значение и следующий шаг |
|---|---|
| `pushed` | commit присутствует в прочитанной удалённой истории; более поздние commits товарища допустимы |
| `updated` | локальная main содержит проверенный итог |
| `current` | нечего отправлять; проверки не запускались |
| `saved` | локальный checkpoint; публикация — отдельный запрос |
| `compared` | записана вся входящая/исходящая порция с авторами |
| `conflict` | исходные файлы не объединены; править только `workspace` |
| `checks-failed` | отправки не было; лог и checkpoint сохранены |
| `verification-failed` | отправка не подтверждена либо тот же результат уже падал |
| `changed` | источник или выбранные файлы изменились во время работы |
| `dirty` | локальные правки мешают применить итог |
| `scope-required` | нужен явный состав порции |
| `approval-required` | есть непросмотренные неопубликованные commits |
| `ownership-conflict` | файл занят другой незавершённой задачей |
| `plan-stale` | план устарел; нужен новый |
| `paused` | сеть запрещена; снятие — только по прямому поручению |
| `busy` | lock занят другой операцией |
| `remote-busy` | remote менялся все попытки; локальные commits сохранены |
| `foreign-operation` | ID принадлежит другой копии или автору |
| `not-resumable` | продолжать нечего |
| `error` | смотреть `stage`, лог и отчёт |

## Вывод и отчётность

Стандартный итог — около 10–12 строк: состояние, задача/план, операция, commit и дерево, remote, счётчики проверок, состав или конфликты, workspace, этап отказа, причина, путь к отчёту и следующий шаг. Полные diff, авторство, fingerprints и логи остаются на диске.

- `--json` — машинный JSON одной строкой документа в stdout.
- `--events` — поток этапов в stderr (по умолчанию этапы печатаются в stderr и без него; `--quiet` их выключает).
- Прогресс никогда не попадает в stdout, поэтому JSON остаётся разбираемым.

Хранение в общем Git-каталоге: `lock`, `paused.json`, `status.json`, `journal.jsonl`, `operations/ID/report.json` с логами и сохранёнными workspace, `tasks/`, `plans/`, `bench/`. Журнал не коммитится; между машинами авторство передаётся историей commits (`Task`, `Sync-Operation`).

## Профили проверок и замеры

Игровая порция запускает `check:game`; изменения sync-инструмента, validate, package/lock, CI или обязательной инструкции — полный `check`. CI всегда выполняет полный `check`.

`npm run bench:sync -- --fixture template --repeats 3` выполняет локальные сценарии (setup, обычная публикация, конфликт→продолжение, вывод CLI) и пишет сырой отчёт в `gamejam-sync/bench/`. Реальный remote не затрагивается.
