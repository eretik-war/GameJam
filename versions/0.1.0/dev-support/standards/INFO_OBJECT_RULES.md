# Общий контракт Info и игровых экземпляров

Принят пользователем 2026-10-11 для всех проектов и новых сущностей. Читать перед проектированием сущности, каталога, фабрики, связей, сохранения или визуального представления. Формат данных и движок выбирает проект; смысл `Info` одинаков во всём семействе.

## Единое представление, качество и взаимодействия — обязательное дополнение26.10.2026

Новое Info должно явно сообщать, где находятся его расчёт, представление, реакции и основные потребители. Поля конкретного проекта могут называться иначе, но связи должны быть читаемыми и проверяемыми, а не скрытыми независимыми реализациями окон.

| Связь Info | Что задаёт |
|---|---|
| QualityInfo или аналогичный справочник модификаторов | Профиль типа/семейства, влияющие параметры и общий пересчёт для состояния экземпляра; качество хранится у копии |
| PresentationInfo / VisualInfo | Состав карточки, единицы/форматы, роли метаданных, общую композицию иконки, ссылку на общий builder/evaluated view |
| InteractionInfo | Декларативные реакции на click/hover/focus/drag/move/scale и ссылку на общий диспетчер |
| UsageInfo / карта владельцев и потребителей | Модули/классы, через которые создают, рассчитывают, отображают, меняют и сохраняют объект; навигацию к единственному владельцу каждого изменения |

Info остаётся общим неизменяемым справочником: в нём разрешены данные и стабильные ссылки/ID общих политик, но не живой DOM/mesh, подписки, захваченные экземпляры, текущее выделение или изменяемые callbacks окна. Живые обработчики и ресурсы принадлежат контроллеру/renderer; они исполняют общую декларативную политику. При JSON-формате ссылка задаётся ID/ключом и разрешается через реестр.

- Карточка, иконка, редактор и игровой runtime читают одно вычисленное представление типа+состояния. Новое окно сначала ищет и переиспользует общий resolver, renderer, форматирование и диспетчер. Локальные формулы качества, копии полей карточки, отдельные бейджи/раскладки или новая логика клика без причины недопустимы.
- Влияния качества задаются для типа/класса предметов, а не для выбранной единичной копии. Изменение профиля применяется ко всем типам, связанным с этим профилем. Базовые Info не изменяются при пересчёте; модификатор применяется один раз от базы. Редактор либо преобразует редактируемое эффективное значение обратно в базу общим методом, либо явно разделяет базу и результат.
- Единая логика взаимодействия действует во всех окнах по умолчанию, включая игру и редактор. Исключение задаётся явной политикой конкретного окна и прямым согласованным требованием пользователя; оно не возникает как случайная копия реализации. Контекст окна предоставляет цель команды (выбрать/перенести и т.д.), а не переписывает общую реакцию предмета.
- Карта потребителей является навигационными метаданными: указывать реальные module/class/handler IDs и владельцев; по возможности проверять/генерировать обратные связи инструментом. Она не должна становиться вторым владельцем игровых параметров или ручным списком runtime-экземпляров.
- Проверять одинаковый результат в нескольких окнах при одном состоянии/Q, независимость экземпляров, отсутствие повторного множителя, стабильность ссылок Info и сохранение общего поведения при добавлении нового интерфейса. Смена состояния/качества должна обновлять все зависимые значения, не только значок.

Это дополнение обязательно для новых сущностей; существующие подсистемы приводятся к нему в объёме поручения пользователя. Сам контракт не разрешает массовую миграцию других проектов, изменение locked runtime или сброс игровых сохранений.

## Данные типа и состояние экземпляра

`Info` — общий неизменяемый справочник или шаблон исходных данных. `Entity` — конкретный игровой экземпляр с собственной идентичностью и текущим состоянием. Экземпляры одного типа ссылаются на один `Info`, а не копируют и не переписывают его при каждом действии.

| Слой | Хранит | Пример |
|---|---|---|
| `EntityInfo` | ID типа, базовые параметры, правила и статические связи по ID | `WeaponInfo`: калибр, ёмкость, базовый урон |
| `Entity` | ID экземпляра, ссылку на Info, персональное состояние и рассчитанные параметры | `Weapon`: патроны в магазине, износ, нагрев, задержка |
| `VisualEntityInfo` | ID того же типа, пути ресурсов, размеры, offsets, настройки анимации/рига | `VisualWeaponInfo`: модель, иконка, точки хвата |
| Renderer | Живые meshes/sprites/DOM, камеры, анимации, их lifecycle | Представление оружия по ID экземпляра |

Текущие HP, патроны, позиция, сторона текущего боя, эффекты, выбор ИИ, таймеры и живые визуальные объекты не принадлежат общему Info. Начальная позиция или сторона допустимы в отдельном справочнике стартовой расстановки; после создания текущая позиция/сторона принадлежат экземпляру.

## Создание и расчёт

- Один каталог и один владелец каждого справочного значения. Исходником может быть TSV, JSON или модуль JS; не вводить дублирующую таблицу ради названия Info.
- Нормализовать и проверять данные при загрузке. Заморозить справочник и вложенные массивы/настройки, которыми пользуются несколько экземпляров; не замораживать Babylon/Pixi/DOM вместе с ним.
- Создавать экземпляры единой фабрикой `createEntityFromInfo(...)`: проверить ссылки, назначить instance ID и начальное состояние, применить выбранный баланс/модернизацию к отдельным параметрам экземпляра.
- Расчёт не должен менять Info или повторно множить уже рассчитанный результат. Эффекты и динамические модификаторы считать от выбранной базы экземпляра; смену базы выполнять явно.
- Базовый параметр читать через `entity.EntityInfo.*`, текущий — через `entity.*` или его геттер. Совместимые aliases допустимы, если не становятся вторым источником данных.
- Новый тип с суффиксом `Info` по этому поручению означает справочник. Когда назначение нового типа неоднозначно, уточнить смысл; не требовать повторного подтверждения уже явно порученной реализации.

## Идентичность и связи

- `typeId` обозначает тип; `id` экземпляра обозначает конкретную сущность. Два экземпляра одного типа могут иметь разные ID и состояние.
- Игровой и визуальный справочники связаны общим `typeId`. Не связывать их порядком строк, именем меша, текстом перевода или похожим названием.
- Связи каталогов хранить через стабильные ID и разрешать через реестр с проверкой неизвестных/повторяющихся ID. Формат ID определяется проектом: цифровые строки Heroes не являются требованием для всех игр.
- Связи между живыми сущностями направлять на instance ID или контролируемую ссылку на экземпляр. Слот — связь владельца с сущностью, а не новый тип оружия.
- Renderer хранит свои объекты по instance ID; визуальная модель не является источником урона, состояния магазина или принадлежности сущности. Удаление/замена представления освобождает только его экземпляр ресурсов, сохраняя общий кэш.
- Каталог preview может показывать другой тип без подмены экипировки игрока. Такое представление явно не связано с боевым экземпляром.

## Сохранения и воспроизведение

В сохранениях хранить ID и необходимое персональное состояние; при загрузке восстановить ссылки через тот же каталог/фабрику. Не сериализовать живые визуальные объекты и не размножать полные Info для каждого экземпляра. Сохранять совместимость старых ID и схем при рефакторинге.

Для replay фиксировать выбранные Info/баланс/стартовую расстановку один раз в заголовке или ссылкой на неизменяемую точную версию. Старый бой не должен зависеть от сегодняшнего каталога. Шаги содержат действия и изменения состояния, а не повтор справочников. Статистика боя и логи изменяемы и не становятся Info только из-за суффикса.

## Проверка проекта

Проверить: каталог не меняется от действий; два экземпляра одного типа независимы; расчёт не удваивает баланс; неизвестные/повторяющиеся ID выявляются; игровые и визуальные типы совпадают; сохранение восстанавливает состояние; удаление представления не ломает другой экземпляр. Для визуально важных сущностей дополнительно проверить реальные игровые ракурсы.

Новые сущности сразу проектировать по этому контракту. Существующие подсистемы мигрировать в объёме конкретного поручения; распространение документации не разрешает переписывать все игры или locked-компоненты.
